# Release and security checklist

This checklist is for the **exact binaries** to be attached to a future stable GitHub Release. An [unsigned Windows preview installer](https://github.com/bevyss/LocalDrop/releases/tag/v0.1.0-preview.1) is available. No signed stable release or VirusTotal result exists yet. A scan of the preview cannot stand in for a scan of the final release file.

1. Build both apps from a reviewed commit and run `scripts/check.ps1` (Windows build and 12 core tests; Android build and unit tests). Record the commit, tool versions, test results, and any warnings in the release notes.
2. Complete the two-device UI and transfer checks in [DEVELOPMENT.md](DEVELOPMENT.md). Confirm the selected Windows device card, all six language choices, name persistence, verification prompts, receive prompts, and file opening. A passing build does not verify the visual layout.
3. Produce a Windows package signed with a trusted publisher certificate and an Android APK signed with a stable release key. Keep signing keys out of this repository. Verify each signature before publication. Do not publish the debug APK as the public installer. Microsoft's [SmartScreen guidance](https://learn.microsoft.com/windows/apps/package-and-deploy/smartscreen-reputation) explains that an unsigned or newly signed app may still show a reputation warning.
4. Compute SHA-256 for each final file with `Get-FileHash <file> -Algorithm SHA256`. Scan those same files with local antivirus and, if appropriate, [VirusTotal](https://docs.virustotal.com/docs/how-it-works). Standard VirusTotal uploads and reports can be shared with its community and security partners, so scan only files intended for public distribution. Keep private builds private unless using its separate private scanning service.
5. Review every detection. VirusTotal is an aggregation of scanner results, not a certificate of safety; a zero-detection result cannot prove a file is safe, and a single detection can be a false positive. [VirusTotal's false-positive guidance](https://docs.virustotal.com/docs/false-positive) directs maintainers to the vendor that raised the detection.
6. Publish a GitHub Release draft with the binaries, hashes, signing information, test summary, and links to scan reports for the exact matching SHA-256 values. Verify the uploaded assets, then publish the release. GitHub documents [release asset management](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository) and [release integrity verification](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/verify-release-integrity).
7. Enable GitHub [CodeQL default setup](https://docs.github.com/en/code-security/how-tos/find-and-fix-code-vulnerabilities/configure-code-scanning/configure-code-scanning) and [private vulnerability reporting](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/configure-for-a-repository) once the repository is public. The repository already includes Dependabot update checks and pull request dependency review; verify that they run after publication. Review security alerts and fix findings before treating a release as stable.

Complete the release steps before changing the installation page to offer a one-click download.
